[Stack-chan](/posts/stackchan-firmware-debugging/)에게 블루 아카이브 케이(ケイ)의 목소리를 입히는 프로젝트의 TTS 부분 기록입니다.
일본어 모델은 금방 배포까지 갔지만, 한국어는 학습이 끝까지 돌았는데도 **모든 문장이 일정한 "웅—" 소리**로만 나오는 문제를 만났습니다.
원인을 찾아간 과정을 정리합니다.

> 학습 데이터는 게임 음성이라 개인 학습용으로만 썼고, 데이터와 모델은 공개하지 않습니다. 데이터 추출 방법도 다루지 않습니다.
{: .prompt-info }

## 1. 일본어: Style-Bert-VITS2 + ONNX DirectML

[Style-Bert-VITS2](https://github.com/litagin02/Style-Bert-VITS2)(SBV2)는 VITS 계열 TTS에 BERT 문맥 특징과 스타일 벡터를 더한 모델입니다.
케이 대사 94개(8.5분)로 일본어 사전학습 모델을 파인튜닝했습니다.

- **학습:** PC GPU가 AMD(RX 9060 XT)라 CUDA가 없어서 Google Colab에서 돌렸습니다.
  - 함정: 공식 노트북이 `PATH`에 `/root/.cargo/bin`만 추가하는데, uv 0.5부터는 `/root/.local/bin`에 설치됩니다. 그래서 `uv pip install`이 **조용히 건너뛰어지고** BERT 가중치도 받지 않은 채 셀이 40초 만에 끝났습니다.
- **체크포인트 선택:** 숫자가 아니라 귀로 골랐습니다. 100 epoch보다 61 epoch가 더 자연스러웠습니다.
- **배포:** PyTorch CPU 추론은 문장당 1.5~11초가 걸리고 RAM을 3.5GB 썼습니다. 펌웨어의 TTS 타임아웃은 8초입니다.

ONNX로 변환해 DirectML(AMD GPU)로 돌렸습니다.

| 추론 방식 | 문장당 시간 | 서버 RAM |
|---|---|---|
| PyTorch CPU | 1.5~11 초 (메모리 압박 시 급증) | 약 3.5 GB |
| **ONNX + DirectML** | **0.3~0.7 초** | 약 750 MB |

SBV2의 기본 서버는 모델에 `onnx_providers`를 넘기지 않습니다. 그래서 모델은 CPU에, 미리 올린 BERT는 DirectML에 올라가 충돌했고, 쓰지도 않는 1.3GB짜리 PyTorch BERT도 항상 읽었습니다. 이 둘을 고친 실행기를 따로 만들었습니다.

## 2. 한국어: 데이터가 모자라다

### 케이 혼자서는 부족

먼저 개인이 만든 한국어 포트(SBV2-KR)로 케이 한국어 대사 89개(8.4분)를 학습했습니다.
Whisper로 받아쓴 문자 오류율(CER)은 이랬습니다.

| 평가 문장 | CER |
|---|---|
| 원본 녹음 | 0.01 |
| 학습에 쓴 문장 | 0.02 |
| **처음 보는 문장** | **0.19~0.24** |

학습 문장은 외웠지만 일반화는 안 됐습니다. 일본어 사전학습 모델에서 출발하니 한국어 발음을 배울 데이터가 8분으로는 부족했습니다.

### 여러 화자로 기반 모델 만들기

게임 전체의 한국어 더빙(화자 224명, 13,872문장, 20.7시간)으로 다화자 기반 모델을 만들고 케이 대사는 10배 반복했습니다. 처음 보는 문장의 CER이 0.11까지 내려갔습니다.
하지만 **된소리(ㄲ ㄸ ㅃ ㅆ ㅉ)** 가 거의 나오지 않았습니다. 원인을 보니 일본어 모델에서 물려받은 음소 임베딩이 거의 움직이지 않았습니다. 예를 들어 ㅅ과 ㅆ 임베딩의 코사인 유사도가 0.99였습니다(일본어에서는 둘 다 "s").

그래서 넥슨게임즈가 공개한 공식 한국어 포트 [io-ml/Style-Bert-VITS2-Korean](https://github.com/io-ml/Style-Bert-VITS2-Korean)으로 옮겼습니다.
된소리를 별도 기호(`k* t* p* s* tɕ*`)로 쓰는 한국어 IPA, g2pk3 기반 G2P, kcbert-large를 씁니다. 다만 코드만 있고 한국어 사전학습 모델은 없어서 기반 모델부터 직접 학습해야 했습니다.

## 3. 34,600 step을 돌렸는데 "웅—"

RTX 4070 Ti 리눅스 머신에서 10 epoch(34,600 step)를 돌렸습니다.
에러 없이 끝났지만 모든 화자, 모든 체크포인트에서 음절 경계도 쉼도 없이 일정한 배음만 이어지는 "웅—" 소리가 났습니다.

### 어디가 고장 났나

| 확인 | 결과 | 판정 |
|---|---|---|
| 합성 입력과 학습 입력 비교 | 완전히 같음 | 추론 코드 정상 |
| 음성 → 음성 인코더 → 디코더 복원 | 원본과 log-mel 상관 0.973 | **디코더 정상** |
| 텍스트만으로 합성 | "웅—", 길이 2.04초(원본 5.65초) | **텍스트 쪽 고장** |
| MAS 정렬 | 토큰 69개 중 약 60개가 첫 0.9초에 몰림 | 정렬 실패 |
| 텍스트 인코더 출력의 시간축 변동 | 0.02 (음성 쪽은 0.77) | 출력이 사실상 상수 |
| 데이터 짝 | 음성 길이–음소 수 상관 0.89 | 데이터 정상 |

VITS는 학습 중에 텍스트 인코더가 만든 사전분포와 음성 잠재변수 사이의 정렬을 MAS(Monotonic Alignment Search)로 스스로 찾습니다.
**텍스트 인코더가 입력과 무관한 상수를 내면 정렬이 생길 수 없고**, 그러면 길이 예측기도 디코더도 텍스트를 따라갈 수 없습니다.

### 정렬을 숫자로 재기

귀로 듣는 대신 체크포인트마다 세 지표를 쟀습니다.

- **m_p std**: 텍스트 인코더 출력이 토큰마다 얼마나 다른지. 0에 가까우면 붕괴입니다.
- **top-3 share**: 가장 많은 프레임을 가져간 토큰 3개의 비율. 작을수록 정렬이 고르게 퍼져 있습니다.
- **dp/actual**: 길이 예측기가 예측한 길이 ÷ 실제 정렬 길이. 1에 가까워야 합니다.

### attention sink 발견

입력을 바꿔 가며 텍스트 인코더 출력이 얼마나 변하는지 봤습니다.

| 모델 | 음소를 섞었을 때 변화 | BERT를 0으로 했을 때 변화 |
|---|---|---|
| 무작위 초기화 | 0.065 | 0.387 |
| ko_base 34.6k | **0.0000** | **0.0000** |

학습된 모델은 입력을 완전히 무시하고 있었습니다.
층별로 추적하니 **0번째 층의 self-attention 출력 크기가 633으로, 입력(33.6)의 19배**였습니다. 이 값은 입력과 무관한 상수라서 LayerNorm을 지나면 모든 위치가 같은 벡터가 됩니다. 첫 층에서 정보가 전부 사라지는 attention sink입니다.

### 범인 후보: BERT 특징의 오프셋

kcbert 특징을 27만 토큰에서 통계 내 보니, 일부 차원에 문장과 무관한 큰 상수가 있었습니다.
27번 차원 평균이 6.7, 389번은 3.1, 1005번은 −3.0이었습니다.
이 오프셋은 `bert_proj`를 거쳐 모든 토큰에 같은 큰 벡터로 더해지고, 그 뒤 $$\sqrt{192} \approx 13.9$$배로 커집니다.
"모든 위치에 같은 큰 성분"은 attention이 입력을 무시하는 쪽으로 무너지기 좋은 조건입니다.

### 작게 먼저: 과적합 시험

전체 데이터로 하루를 쓰기 전에 화자 1명, 130문장으로 처음부터 학습하며 정렬이 생기는지 봤습니다(값은 m_p std / top-3 share).

| step | BERT 그대로 | BERT 0 (음소만) | **BERT 표준화 ×0.1** |
|---|---|---|---|
| 1k | 0.007 / 0.25 | 0.004 / 0.28 | 0.004 / 0.25 |
| 5k | 0.049 / 0.33 | 0.029 / 0.22 | 0.049 / 0.25 |
| 6k | – | 0.084 / 0.20 | **0.102 / 0.21** |
| 10k | – | 0.100 / 0.19 | **0.180 / 0.17** |

- 원래 BERT를 그대로 넣으면 top-3 쏠림이 오히려 커졌습니다(0.25 → 0.33).
- BERT를 빼면 6~7k step에서 정렬이 생겼습니다. 파이프라인 자체는 정렬을 배울 수 있다는 뜻입니다.
- **BERT를 차원별로 표준화하고 0.1을 곱하면** 같은 시점에 정렬이 생기고 그 뒤로 더 빨리 좋아졌습니다.

수정은 TextEncoder 입력 직전에 한 줄을 넣은 것입니다(학습과 추론에 똑같이 적용).

```python
def _bert_input(bert):            # bert: (B, 1024, T)
    mu, sd = bert_stats["mean"], bert_stats["std"]   # 학습 데이터에서 미리 계산
    return (bert - mu[None, :, None]) / sd[None, :, None] * 0.1
```

### 전체 데이터로 다시: ko_v2

1. 과적합 시험에서 정렬이 잡힌 10k 체크포인트로 초기화
2. BERT 표준화 ×0.1
3. 처음 10k step은 판별기 없이 generator만 학습(warm-up), 그 뒤 GAN

이렇게 하니 전체 데이터에서도 정렬이 유지됐습니다.

| 체크포인트 | m_p std | top-3 | dp/actual |
|---|---|---|---|
| 기존 ko_base 34.6k | 0.020 | 0.62 | 0.55 |
| **ko_v2 5k** | **0.142** | **0.25** | 0.67 |
| ko_v2 100k | 0.156 | 0.23 | 0.72 |

드디어 문장을 읽기 시작했습니다.

## 4. 말은 하는데 아직 남은 문제

총 207,640 step까지 학습한 뒤, 같은 40문장을 경로별로 합성해 Whisper로 받아쓰기 했습니다.

| 경로 | CER | 된소리 음절 유지 |
|---|---|---|
| 원본 녹음 | 7.7% | 93% |
| 음성 → 디코더 복원 | 19.8% | 76% |
| **TTS** | **26.3%** | **76%** |

합성 설정도 훑어서 `sdp_ratio 0.5`, `length_scale 1.2`일 때 CER 21%로 가장 좋고 길이도 원본에 가까웠습니다.

### 된소리: 격음 쪽으로 쏠린다

"이건 달/딸/탈이에요" 같은 최소대립쌍 300개를 합성해 강제 선택으로 채점했습니다.

| | 평음 | 경음 | 격음 | ㅆ |
|---|---|---|---|---|
| 정답률 | 35% | 31% | 70% | **0%** |

문장 속에서는 문맥 덕분에 76%가 유지되지만, 단어만 떼어 놓으면 평음과 경음이 격음으로 들립니다(굴 → 쿨). ㅆ은 한 번도 ㅆ로 들리지 않았습니다.
G2P의 경음화 표기를 점검했더니 62개 중 60개가 맞아서, 라벨 잡음 가설은 기각했습니다.

### 기계음: 디코더의 고음역

제 귀에는 여전히 기계음처럼 들립니다. 실제 케이 녹음 30개와 비교하면 합성음은

- 3~16 kHz 에너지가 2~3 dB 낮고,
- 3~10 kHz 스펙트럼 평탄도가 높습니다(0.24 vs 0.17).

고음역이 배음이 아니라 잡음으로 채워진다는 뜻입니다. 노이즈 설정을 바꿔도 그대로라서 디코더 문제로 봅니다.
일본어 모델은 잘 학습된 사전학습 디코더를 물려받았지만, 한국어 기반 모델의 디코더는 처음부터 학습했기 때문입니다.

### 다음 단계

1. 정렬은 건드리지 않도록 나머지를 고정하고 디코더만 재학습 (성숙한 SBV2 디코더에서 warm start)
2. 된소리 대립 개선 (된소리 문장 가중치, BERT 비중 더 낮추기)
3. 마지막으로 케이 파인튜닝

## 배운 것

- **사전학습 특징을 붙일 때는 통계부터 봅니다.** 평균이 0이 아닌 큰 상수 성분은 attention을 무너뜨릴 수 있습니다. 표준화 한 줄로 해결됐습니다.
- **"학습은 됐는데 결과가 이상하다"면 모듈을 하나씩 떼어 시험합니다.** 디코더 복원, 텍스트만 합성, 정렬 시각화로 고장 난 곳을 한 시간 안에 텍스트 인코더로 좁혔습니다.
- **큰 학습 전에 작은 과적합 시험을 합니다.** 130문장으로 30분 돌린 시험이 몇 시간짜리 전체 학습 여러 번보다 많은 걸 알려 줬습니다.
- **귀 대신 지표를 만듭니다.** m_p std, top-3 share, Whisper CER, 최소대립쌍 정답률 덕분에 체크포인트끼리 비교할 수 있었습니다.
- Colab에서 되던 스크립트가 로컬 리눅스에서 안 되면, Colab에 미리 깔린 패키지(`tensorboard`, `soxr` 등)를 의심합니다.
